# WLED plugin user-experience audit

Audit started September 10, 2026 (America/Chicago). Baseline: `d441a85`.
Reference: pinned WLED v16.0.1, commit `29b389df1c1aaec6ff53aea742d17063b985906c`.

## Result and scope

The common lighting/setup workflows passed the checks below after fixes. This is
not a claim that every effect, peripheral, third-party client or physical output
has been certified. Browser mutations used disposable local fixtures. FPP04
(`192.168.50.167`) was checked read-only, apart from the normal idle plugin upgrade.
No native controller lighting commands or FPP output mappings were changed on it.

## Fixed in this audit

| Finding | Result |
|---|---|
| Actions displayed generic “Completed”, a section confirmation, and sometimes raw JSON at the foot of the page | One action-result location per section. Raw response dumps and generic success paragraphs removed. Persistent state summaries remain distinct from action results. |
| Request failures could leave “Working...” indefinitely or show a JSON parsing exception | Mutation requests have a 15-second timeout and readable errors at the relevant control. A timeout does not claim the server rejected the change. |
| Authorization failure scrolled to a collapsed access section | Access state is refreshed and the section opens. Direct links/navigation to collapsed setup sections open their controls. |
| Lighting buttons looked usable before browser authorization | Lighting actions require both healthy ambient permission and browser access. |
| Failed schedule save left Save disabled | The same draft can be retried. Instructions now match Add → Preview → Save. |
| Blank numeric setup inputs could silently become zero | Required setup numbers are checked before saving; blank mapping numbers remain invalid instead of becoming channel/pixel zero. |
| Multiple clicks could overlap setup saves | Save buttons remain disabled for their save operation. |
| Saving network settings replaced unfinished advanced JSON | Network saves preserve unfinished JSON and unrelated draft keys. |
| “Reload” did not explain that unsaved edits were discarded | Buttons explicitly say “Discard edits and reload”. |
| Native-device queue acceptance looked like delivery success | Text says “Command queued” and directs users to delivery status. |
| Upstream UI offered unsupported segment blend/sound/set choices | Unsupported choices are disabled with explanations. |
| Main-screen “Files” opened preset import, not a file browser | Label now says “Presets”; accessible name explains import/backup. |
| A selected-effect positioning interval was created for every status update | The generated upstream UI creates one interval per page. Browser instrumentation verified one after repeated updates. |

## Remaining UX work, in priority order

Historical findings below: consult [alpha 2 status](ALPHA_2.md) for subsequent
implementation and the current remaining acceptance work.

1. **Import the user's FPP layout.** Named strings/models and matrix dimensions do not yet become default segments. A visual editor for combining pixels across ports also remains unimplemented. Do not present the current channel rows as that feature.
2. **Make native-device management understandable without JSON.** Discovery links work, but enrollment still requires copying an address; per-device/group commands use JSON; delivery/recovery details are technical. Add “Add this device”, mode explanation, friendly status and effect/preset pickers.
3. **Finish preset/playlist rejection recovery in the upstream main UI.** It updates its local preset list optimistically before the server acknowledges a save. Linux rejection messages are shown, but a rejected save can require reloading to reconcile the list. Test failure/retry/conflict behavior before calling this polished.
4. **Expose advanced integrations through guided settings.** MQTT/Home Assistant setup and custom pixel maps still require advanced configuration. A color-stop editor would remove the need to write palette JSON.
5. **Offer a combined setup backup/restore flow.** Preset and palette downloads exist; a guided whole-plugin backup is missing. Explain exactly which settings and show locks a restore includes.
6. **Improve long-page navigation and control explanations.** The primary controls and completed sections are clearer, but the page is still long. Disabled upstream tools (such as PixelForge) need a consistent feature-limit explanation, and the compatibility list should eventually use friendly names instead of effect IDs.
7. **Broaden device/browser/accessibility acceptance.** Safari/iOS, keyboard-only and screen-reader workflows, rapid repeated edits, cross-tab conflicts, long-running playlists, and long-duration browser stability need dedicated passes. This session does not exhaust their combinations.

## What differs from native WLED

### Follow-up implementation

The original gap list above records the audit findings. This follow-up adds:

- Single state-driven buttons for ambient permission, light power and nightlight. Labels show the next action; failed writes do not flip state. FPP setup uses rounded outlines with readable neutral, green and paused amber states. WLED retains its native controls with an explicit Turn on / Turn off power label.
- FPP layout selection, preview and staged import for named channel models and pixel strings, including supported rectangular matrices. Apply setup creates the named segments on restart. Validation does not alter live state; a runtime lock precedes migration. Unchanged imports preserve later segment edits.
- Discovery enrollment into the configuration draft, guided individual/group effect and preset commands, and readable delivery status. Queued or UDP-sent commands are not described as confirmed physical delivery.
- Preset and playlist saves/deletes wait for server acknowledgement and reload the authoritative catalog. Rejected saves retain their draft; rejected deletes retain the preset.
- `/json/eff`, `/json/pal`, sampled `/json/live`, and redirects from common native settings/liveview routes to the corresponding Linux setup section.
- Read-only runtime render timing and FPP acknowledgement diagnostics at `/api/diagnostics`.

Still open: arbitrary cross-port virtual segment editing, mixed RGB/RGBW canvases,
custom/3D model import, guided MQTT/HA and palette editing, full setup restore,
broader accessibility/browser acceptance, and physical sync/takeover/recovery
acceptance. Unsupported effects and excluded hardware features are unchanged.

Verification: 137 Python tests passed. Browser checks passed for settings,
main controls, rejected preset save/delete recovery, and single state buttons,
including failed changes and text contrast in both themes. Layout enrollment
and guided device payloads were exercised against disposable/mocked devices.
These checks do not certify physical lighting.

Live follow-up: code revision `7326bab` installed successfully on FPP04 at
`192.168.50.167` (Pi 4 Model B, FPP 10.0, 64-bit). The 21 existing read-only
routes, five new API routes, device-control asset and settings redirects passed.
Runtime status reported healthy observation, allowed ambient and no fault.
A 10-second sample of its existing 1,000 RGB-pixel Candle Multi workload measured
39.72 fps at a configured 40 fps, mean renderer time 0.396 ms, and peak renderer
time since startup 1.353 ms. FPP acknowledgement advanced. This is a short
operational sample, not the full benchmark or physical-light acceptance test.
FPP04 contained no saved importable channel models or pixel strings; the UI
reported that condition. Initial 404/503 responses while installation replaced
assets and restarted services cleared after completion and reload.

| Category | What remains / how to account for it |
|---|---|
| Effects | 220 preserved IDs; 129 supported for a strip, 171 for the matrix fixture. Unsupported IDs stay excluded. Remaining effects need real Linux dependency support and visual validation, not ID renaming. |
| Geometry | One virtual canvas and explicit global ledmap. Automatic FPP-model import, arbitrary cross-port virtual segments, and a guided mixed matrix/string editor remain gaps. |
| Segments/colors | Up to 32 segments. No hardware CCT bus/current limiting; non-default segment blend modes, segment sets and sound simulation are unavailable. Ordinary transitions are supported; custom transition styles are not. |
| Presets/playlists | Supported subset includes selective saves, imports, shuffle, timers and local interrupted-entry recovery. No boot-preset overrides, nested playlists, reference chains/random command expressions or general HTTP-command parity. Native-controller playlist position cannot be reconstructed through the exposed native state API. |
| Web/API | Main WLED UI is reused; most embedded settings pages are replaced by Linux setup. No complete `/json/cfg`, legacy `/win`, upstream liveview route, arbitrary filesystem editor or fragmented-WebSocket request parity. Linux pixel preview is the available replacement for Peek. Native aliases/third-party assumptions need compatibility tests. |
| Network/integrations | Discovery, notifier sync, MQTT and basic HA discovery exist. Native sync, HA's native WLED integration, network-loss recovery and mixed-routing takeover still need real-hardware acceptance. Native-controller authentication is not implemented. Custom palette files are not automatically distributed to peers. |
| Hardware functions | ESP flashing/OTA, Wi-Fi provisioning, ESP-NOW, GPIO/relays/buttons, audio input, arbitrary usermods, Philips Hue and file fonts are excluded. Some can be ported with new Linux backends; others belong in FPP or remain out of scope. |
| Pixel transport | FPP owns physical buses and DDP/E1.31/Art-Net. The runtime does not independently send pixel streams. FPP output configuration remains required. |
